# BASELINE.txt -- the shrinking ratchet for TypeSpecCorpusTest (ADR 0007, plan 04 M6a-M6f).
#
# One entry per corpus-relative path currently permitted to fail either of ADR 0007 D2's two
# properties (a PsiErrorElement, or an unclaimed leaf token).
#
# Format (post-M6b revision -- see plan 04 M6b tsp-tester report):
#   <corpus-relative-path>  # rowN[, rowM, ...]: <short construct name> (observed: <evidence>)
#
# Each entry lists EVERY plan-04 row (docs/plans/04-grammar-corrections.md's table) whose
# construct was actually seen blocking that file's parse in *this* diagnostic pass -- not a
# one-shot categorization made once and never revisited. "Observed" means: re-run the file
# through TypeSpecParserDefinition, read the actual PsiErrorElement message(s)/line(s) (and,
# where the parser gives up entirely, the resulting unclaimed-leaf locations), and match each
# distinct failure to a row by its construct shape, not by assumption.
#
# Why this matters (discovered the hard way during M6b hand-review): recording only the
# single lowest-numbered row at baseline-creation time goes stale the moment an earlier row
# is fixed by a later milestone -- the label still names the row that USED to be first, while
# the file now fails for an entirely different, unrelated reason (or, worse, a reason that
# was always there but was masked by the first one and never diagnosed). Two concrete cases
# from this pass: six `real/**` files labelled "row1: decorator on a model member" were
# actually blocked by row3 (`model X is Y;`) or row4 (triple-quoted strings) -- row1 had
# already been fixed in commit 9aba27f, and the label was never revisited. Separately, roughly
# half of the `stdlib/protobuf/test/scenarios/**` entries labelled "row5: comma-separated
# model member" were, on re-diagnosis, actually blocked by row7 (`...Input` spread operation
# parameters) -- M6b's fix to row5 had landed silently underneath a stale row5 label.
#
# Multi-row entries are real, not a hedge: a file can fail for more than one independent
# reason, and fixing only the first-listed row will surface the next one, not clear the file.
# Whichever row is listed first is the one whose failure the parser reports/recovers from
# earliest in the file; later rows are separately confirmed present further down the same file.
#
# The ratchet is bidirectional and enforced by TypeSpecCorpusTest.testCorpusMatchesBaseline:
#   - a file failing that is NOT listed here fails the test (undeclared regression);
#   - a file listed here that now PASSES fails the test (undeclared fix -- remove the line).
# The test itself only checks pass/fail per file; the row numbers in the reason column are
# documentation for the next milestone, not something the test parses or verifies -- so they
# carry no weight beyond helping the next diagnosis start from the right place. Re-diagnose,
# don't trust, whenever a row lands.
#
# This file is deleted entirely at M6f (plan 04), once the corpus is a zero-baseline assertion.
